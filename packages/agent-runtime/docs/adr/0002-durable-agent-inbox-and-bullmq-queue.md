# Durable agent inbox + BullMQ queue

Ticket #21. A dedicated Redis (`agent-redis`, separate from Twenty's own `redis`) backs a BullMQ queue, fronted by a durable inbox table (`agent_inbox_events`) in the agent database from ticket #20. `AgentInboxService.submit(actionId, jobName, payload)` is the only entry point: it commits the event to Postgres before enqueueing it, so a crash between "received" and "enqueued" never silently drops work, and `AgentInboxWorkerService` processes jobs with bounded retries and exponential backoff.

**Why the Postgres row is the duplicate-protection record, not BullMQ's jobId.** BullMQ treats two `queue.add()` calls with the same `jobId` as duplicates only while the first job still exists in Redis. Once a completed (or failed) job is removed — which `removeOnComplete`/`removeOnFail` do by design, to bound Redis growth — the same `jobId` can be re-added and will run again. That's exactly wrong for this ticket's "a completed job is not reprocessed on redelivery or restart" acceptance criterion. `AgentInboxService.submit` avoids this entirely: `insertIfAbsent` is the single check for whether this action ID has ever been submitted, via a plain `INSERT ... ON CONFLICT (action_id) DO NOTHING`, and `queue.add` only runs when that insert actually happened. BullMQ's own jobId still gets set to the action ID as a second, redundant layer, but the correctness of duplicate protection never depends on it.

**Two different kinds of "resume after a restart," two different mechanisms.** A worker killed mid-job — the job is still active in Redis — resumes through BullMQ's own stalled-job recovery once a worker restarts and finds the lock expired; nothing in this package needs to implement that. A crash between the Postgres insert and the `queue.add` call (or a Redis job somehow lost despite persistence) is a different gap BullMQ can't see at all, since nothing was ever enqueued for it. `AgentInboxService.recoverPendingEvents`, run at boot, closes that gap: it reads every inbox row still `pending`/`processing`, and for each one with no matching job in Redis (`queue.getJob(actionId)` returns nothing), re-enqueues it. Don't conflate the two — adding stalled-job-style logic to `recoverPendingEvents` (or vice versa) would be solving a problem that mechanism doesn't have.

**Terminal status is written from Worker events, not inside the processor.** The processor (`AgentInboxWorkerService.process`) marks the inbox row `processing` on every attempt, but can't itself tell whether a thrown error is about to be retried or has exhausted BullMQ's configured attempts — that's a Worker-level fact (`opts.attempts`, current `attemptsMade`, whether `UnrecoverableError` was thrown) that would be fragile to re-derive per job. `AgentInboxWorkerService` listens to the Worker's own `completed`/`failed` events instead and writes the terminal row state there. This does mean the DB write happens slightly after the event fires (not awaited by BullMQ itself) — acceptable for status bookkeeping, not something anything else's correctness depends on.

**BullMQ's `Queue` and the underlying `ioredis` connection are DI tokens, not constructed inline.** `AGENT_REDIS_CONNECTION`/`AGENT_INBOX_QUEUE` (`agent-inbox-queue.provider.ts`) are factory providers so `AgentInboxService` can be unit-tested the same way `ControlledToolApiService` is tested against a mocked `TwentyGraphqlClientService` — a real network client swapped for a mock in tests, not something the service constructs itself. `AgentInboxWorkerService` doesn't get this treatment: nothing about its correctness needs a mocked BullMQ `Worker`, since the interesting logic (`processDemoJob`, `runJob`) is already exported as plain functions tested directly.

**The demo job proves the acceptance criteria, not just wires something up.** `processDemoJob` throws on `attemptsMade === 0` and succeeds after — a real transient failure, not a simulated no-op, so "bounded retries with backoff" is proven against actual retry behavior the first time this ever boots against a fresh database. Submitted under a fixed action ID (`agent-inbox-demo`), the same convention as `AgentGraphService`'s fixed thread ID and `ControlledToolApiService`'s demo action ID: every boot after the first finds the row already `completed` and `submit` correctly declines to re-enqueue it, which is itself the live proof that duplicate protection survives a restart.

**`app.enableShutdownHooks()` was missing entirely.** Without it, Nest never calls `onModuleDestroy` on `SIGTERM`/`SIGINT` — every prior ticket's graceful-shutdown logic (`TelegramBotService`'s poll-drain, `AgentGraphService`'s `checkpointer.end()`) was dead code outside of unit tests, not just this ticket's `queue.close()`/`connection.quit()`. Added in `main.ts` as part of this ticket since it's the first place a graceful queue/worker shutdown was actually needed to test the mid-job-kill acceptance criterion properly, but it fixes the same gap for every module that had it.

**Failed jobs stay reviewable, not through a bespoke dashboard.** `removeOnFail: { count: 5000 }` bounds retention without deleting recent failures; the Postgres row for a failed event carries the actual error message. Consistent with how Phoenix and llm-guard are handled elsewhere in this repo (SSH tunnel / direct inspection, no bespoke UI): review a stuck job via BullMQ's own tooling against `agent-redis`, or a direct query against `agent_inbox_events`, not a new HTTP endpoint this ticket doesn't need.
