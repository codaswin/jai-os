# Durable agent inbox + BullMQ queue

Ticket #21. A dedicated Redis (`agent-redis`, separate from Twenty's own `redis`) backs a BullMQ queue, fronted by a durable inbox table (`agent_inbox_events`) in the agent database from ticket #20. `AgentInboxService.submit(actionId, jobName, payload)` is the only entry point: it commits the event to Postgres before enqueueing it, so a crash between "received" and "enqueued" never silently drops work, and `AgentInboxWorkerService` processes jobs with bounded retries and exponential backoff.

**Why the Postgres row is the duplicate-protection record, not BullMQ's jobId.** BullMQ treats two `queue.add()` calls with the same `jobId` as duplicates only while the first job still exists in Redis. Once a completed (or failed) job is removed — which `removeOnComplete`/`removeOnFail` do by design, to bound Redis growth — the same `jobId` can be re-added and will run again. That's exactly wrong for this ticket's "a completed job is not reprocessed on redelivery or restart" acceptance criterion. `AgentInboxService.submit` avoids this entirely: `insertIfAbsent` is the single check for whether this action ID has ever been submitted, via a plain `INSERT ... ON CONFLICT (action_id) DO NOTHING`, and `queue.add` only runs when that insert actually happened. BullMQ's own jobId still gets set to the action ID as a second, redundant layer, but the correctness of duplicate protection never depends on it.

**Two different kinds of "resume after a restart," two different mechanisms.** A worker killed mid-job — the job is still active in Redis — resumes through BullMQ's own stalled-job recovery once a worker restarts and finds the lock expired; nothing in this package needs to implement that (verified live: a hard `docker kill` mid-job followed by a restart resumed and completed the job via BullMQ's own mechanism, no code of ours involved in that resumption). A crash between the Postgres insert and the `queue.add` call (or a Redis job somehow lost despite persistence) is a different gap BullMQ can't see at all, since nothing was ever enqueued for it. `AgentInboxService.recoverPendingEvents` closes that gap: it reads every inbox row still `pending`/`processing`, and for each one with no matching job in Redis (`queue.getJob(actionId)` returns nothing), re-enqueues it. Run at boot *and* on a 60s interval, not boot-only — `submit()` commits the Postgres row before calling `queue.add`, so if `queue.add` itself throws (a transient Redis blip), the row is stuck `pending` with no corresponding job until something re-checks it; on a long-running deploy, boot-only recovery could leave that gap open for days. Don't conflate this with stalled-job recovery — adding stalled-job-style logic to `recoverPendingEvents` (or vice versa) would be solving a problem that mechanism doesn't have.

**Terminal status is written inside the awaited processor, not from Worker events — this was wrong in an earlier draft.** BullMQ's Worker fires `'completed'`/`'failed'` on every attempt, including ones that go on to retry, not only once retries are exhausted (confirmed by reading `worker.js`'s `handleFailed`, which calls `moveToFailed` and unconditionally emits `'failed'` regardless of whether a retry was scheduled). Listening to those events to write the terminal inbox status — the first version of this code did — meant a job's row flipped to `status: 'failed'` with a real error message during every backoff window, even though it was about to retry and likely succeed; the demo job itself hit this every single boot. Fixed by moving the decision inside `AgentInboxWorkerService.process`, computed synchronously before BullMQ ever sees the failure: `isFinalAttempt(job, error)` checks `job.attemptsMade + 1 >= (job.opts.attempts ?? 1)` (attemptsMade going into this attempt, plus this one, against the configured ceiling) or an `UnrecoverableError`, and only then calls `markFailed`. A DB failure inside `runJob` itself is handled the same way, inside that same catch — but `markCompleted`'s own failure is deliberately *not* caught by that logic: if the job's work succeeded but the completion write throws, re-throwing unmarked lets BullMQ retry the whole attempt (which retries the write too) rather than recording a false "failed" status for a job whose real work already succeeded.

**BullMQ's `Queue` and the underlying `ioredis` connection are DI tokens, not constructed inline.** `AGENT_REDIS_CONNECTION`/`AGENT_INBOX_QUEUE` (`agent-inbox-queue.provider.ts`) are factory providers so `AgentInboxService` can be unit-tested the same way `ControlledToolApiService` is tested against a mocked `TwentyGraphqlClientService` — a real network client swapped for a mock in tests, not something the service constructs itself. `AgentInboxWorkerService` doesn't get this treatment for its own `Worker`: nothing about its correctness needs a mocked BullMQ `Worker`, since the interesting logic (`processDemoJob`, `runJob`, `isFinalAttempt`) is already exported as plain functions tested directly.

**Shutdown order is explicit code, not a Nest lifecycle-hook assumption — this was also wrong in an earlier draft.** Nest runs every provider's `onModuleDestroy` within a module *concurrently* (`Promise.all`, confirmed by reading `@nestjs/core`'s `on-module-destroy.hook.js`), not sequentially in dependency order. `AgentInboxRepository`'s shared `pg.Pool` is written to by both `AgentInboxService` and `AgentInboxWorkerService` right up until each one's own close logic finishes, so neither `AgentInboxRepository` nor `AgentInboxWorkerService` implements `OnModuleDestroy` — closing is a plain `close()` method on each, and `AgentInboxService.onModuleDestroy` calls them in the required order itself: `worker.close()` (waits for any in-flight job's own processing promise, including its `markCompleted`/`markFailed` write, since that write is now inside the awaited processor per the fix above) first, then the queue/connection, then `repository.close()` last. Verified live: a graceful `docker compose stop` still completes in under a second with this ordering, so it isn't hiding a hang.

**The demo job proves the acceptance criteria, not just wires something up.** `processDemoJob` throws on `attemptsMade === 0` and succeeds after — a real transient failure, not a simulated no-op, so "bounded retries with backoff" is proven against actual retry behavior the first time this ever boots against a fresh database (verified live via the raw BullMQ job hash: `atm: 2`, a recorded `stacktrace` from the first failed attempt, and `returnvalue: {"echoed":true}` from the second). Submitted under a fixed action ID (`agent-inbox-demo`), the same convention as `AgentGraphService`'s fixed thread ID and `ControlledToolApiService`'s demo action ID: every boot after the first finds the row already `completed` and `submit` correctly declines to re-enqueue it, which is itself the live proof that duplicate protection survives a restart (verified live: the job's `atm`/`finishedOn` and the inbox row's `updated_at` were byte-for-byte unchanged across a restart).

**`app.enableShutdownHooks()` was missing entirely.** Without it, Nest never calls `onModuleDestroy` on `SIGTERM`/`SIGINT` — every prior ticket's graceful-shutdown logic (`TelegramBotService`'s poll-drain, `AgentGraphService`'s `checkpointer.end()`) was dead code outside of unit tests, not just this ticket's. Added in `main.ts` as part of this ticket since it's the first place a graceful queue/worker shutdown was actually needed to test the mid-job-kill acceptance criterion properly, but it fixes the same gap for every module that had it.

**Failed jobs stay reviewable, not through a bespoke dashboard.** `removeOnFail: { count: 5000 }` bounds retention without deleting recent failures; the Postgres row for a failed event carries the actual error message. Consistent with how Phoenix and llm-guard are handled elsewhere in this repo (SSH tunnel / direct inspection, no bespoke UI): review a stuck job via BullMQ's own tooling against `agent-redis`, or a direct query against `agent_inbox_events`, not a new HTTP endpoint this ticket doesn't need.

**`payload`/`result` are explicitly `JSON.stringify`'d before binding to a `jsonb` column.** `pg` only auto-serializes a plain object/array parameter; a bare top-level string is sent as raw unquoted text and fails `jsonb`'s implicit cast (a number or boolean parameter happens to produce valid JSON text as a coincidence of how `pg` stringifies them, which is exactly the kind of thing not to rely on). `AgentInboxRepository`'s `toJsonParam` helper stringifies explicitly for every shape, since a future job handler (ticket #22's approval decision, plausibly a bare boolean or string) shouldn't be able to crash `markCompleted` depending on what type its result happens to be.

**Residual limitation, accepted rather than solved:** if a job's real work succeeds but its `markCompleted` write fails on every one of its `attempts` retries, the BullMQ job ends up `failed` in Redis while the inbox row is left at `processing` forever — `recoverPendingEvents` won't touch it (a matching job still exists in Redis), so it's neither silently re-run nor auto-corrected, just stuck showing the wrong status until someone looks. Fully closing this needs an outbox/saga pattern with idempotent job handlers, which is out of scope here — the acceptance criteria this ticket is built against are about duplicate *submission* and restart *resumption*, not exactly-once *execution* semantics for an arbitrary handler's side effects.
