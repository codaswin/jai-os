# Arize Phoenix tracing, and a handoff for what's next

Ticket #19. Every `LlmService.generate()` call and every `ControlledToolApiService.callTool` call now appear as a trace in one Phoenix project (`jai-os-agent-runtime`), not two separate views. `generate()` tracing is automatic — `registerTelemetry(new OpenTelemetry(...))` from `@ai-sdk/otel` is registered once at boot (`src/tracing/tracing.ts`), and every `generateText()` call picks it up with no per-call code. Tool-call tracing is manual: `ControlledToolApiService.callTool` is wrapped with `traceTool` (`@arizeai/openinference-core`) in the constructor, so every caller gets a `TOOL`-kind span whether they know tracing exists or not. Both paths share the same `NodeTracerProvider` and `OpenInferenceBatchSpanProcessor`, which is what puts them in one project instead of two.

`ControlledToolApiService` also gained an `onModuleInit` that runs a demo `lookup-person-by-email` call at boot (fixed fake email, logged, try/caught) — before this ticket, nothing in the running app ever actually called `callTool`, so there was no real call to trace. Same role `AgentGraphService.runDemo` already played for the persistence layer.

**ESM-only dependencies in a CommonJS package.** `@ai-sdk/otel` and `@arizeai/openinference-vercel` ship ESM-only — no CJS `require` export condition. This package stays CommonJS (Nest decorators need `experimentalDecorators`, and migrating the whole package to ESM wasn't in scope for this ticket). A plain `await import(...)` doesn't fix it: under `module: "commonjs"`, TypeScript downlevels dynamic import to `Promise.resolve().then(() => require(...))`, which hits the exact same resolution failure — confirmed by inspecting the compiled output, not assumed. The fix is `importEsm` in `tracing.ts`: a `new Function('specifier', 'return import(specifier)')` indirection that TypeScript's compiler can't see into and therefore can't downlevel, so it stays a genuine dynamic import Node's loader resolves at runtime. This is flagged debt, not a pattern to copy — if a third ESM-only dependency shows up here, that's the signal to reconsider the package's module system instead of adding a third `importEsm` call.

**Tracing is best-effort, not a boot dependency.** `bootstrap()` in `main.ts` wraps `setupTracing()` in try/catch and logs rather than crashing; `agent-runtime` does not `depends_on: phoenix` in `docker-compose.yml`. Both were verified live: the app starts and works correctly with the Phoenix container entirely absent. The rest of this package already treats non-critical infra this way (`AgentGraphService.runDemo`, the tool-call demo above) — tracing failing must never take down the Telegram bot or the Controlled Tool API, which have nothing to do with it.

**Phoenix's image has no shell at all** (not even `/bin/sh`), discovered the same way the `llm-guard` healthcheck gap was in ticket #18: by actually trying it, not by trusting the vendor's docs. Its healthcheck in `docker-compose.yml` has to use the exec form running `python3` directly (`["CMD", "python3", "-c", "..."]`), not the usual shell-string form.

**Current state as of this ADR:** `main` has tickets #15–#18 and #20 merged (scaffold, Telegram, LLM wiring, LLM Guard, agent persistence DB — plus the CI workflow, payload-validation/shutdown-race hardening in ADR 0001, and this package's `CONTEXT.md`). **Next unblocked ticket: #21, "Durable agent inbox + BullMQ queue."** Blocked by #16 (Telegram bot) and #20 (agent persistence DB), both already on `main`. Also now unblocked, if a different order is preferred: #23 ("Infra alerts over Telegram," needs only #16) and #24 ("Backups extended to the agent database," needs only #20) — but #21 is the one that unblocks the rest of the chain (#22 Approvals needs #21; #25, the end-to-end proof action, needs #21 and #22), so it's the natural next pick.

Where to find the spec: `gh issue view 21` for the ticket itself, `gh issue view 14` for the parent Phase 2 spec, and `jai-os-docs/08-build-phases.md` for how Phase 2 fits the larger build. `CONTEXT.md` in this package has the vocabulary and constraints already established (Controlled Tool API, Action ID, fail-closed LLM Guard, the scanner-isolation trick) — read it before touching `ControlledToolApiService` or `LlmService`, since #21's durable inbox is exactly what's meant to replace the in-memory Action ID tracking `CONTEXT.md` already flags as interim.

**Working pattern established across tickets #15–#19**, worth repeating: branch off the current stack tip, implement with tests, run `docker compose build agent-runtime` plus a real `docker compose up` boot check (not just unit tests — this repo has caught real bugs this way: the llm-guard and Phoenix healthcheck shell gaps, the ESM/CommonJS interop break, the missing `yarn.lock` workspace entry), run `/code-review`, apply real findings, then open a PR stacked on the previous ticket's branch.
