# Twenty-embedded widget entry point for the Manager

Ticket #45 — the third and last Phase 3 entry point, after #43's agent core and #44's Telegram wiring. A logged-in Twenty user (Admin only) can now talk to the Manager from inside Twenty itself, via a small front component widget. This is the first time anything in `agent-runtime` is reachable from outside the private Docker network, so most of the real design and the real bugs here are about that boundary, not the agent itself.

## Two new pieces either side of the boundary

**Server side** (`packages/agent-runtime/src/manager-agent/`): `TwentyCurrentUserService.verifyToken(token)` takes whatever bearer token the widget forwards and uses it exactly the way any other bearer token is used against Twenty's own GraphQL API — not a separate "introspect this token" endpoint. `ManagerWidgetController` (`POST /widget/message`) extracts the token, verifies it fresh on every single request (no caching), rejects non-Admins with 403, and routes to `ManagerAgentService.handleMessage` under channel `'widget'` keyed by the *verified* user id — never a client-supplied `conversationKey`, so a crafted request body can't impersonate another user's conversation thread.

**Client side** (`packages/twenty-apps/internal/manager-widget/`): a new, minimal Twenty App — not an addition to an existing one, since none of the existing internal apps (`invoice`, `real-estate`) has any reason to own a cross-cutting Manager chat UI. One front component (`manager-chat.front-component.tsx`) renders a message list, text input, and send button; on each send it calls `frontComponentHostCommunicationApi.requestAccessTokenRefresh()` for a fresh Application Access Token and POSTs `{ text }` with that token as a Bearer header to `/agent-api/widget/message`.

## Why a Twenty session token, not a new credential

Twenty already has a token type built for exactly this — a front component calling back out as the current user — called an Application Access Token, obtained via `requestAccessTokenRefresh()` and validated by the same `JwtAuthStrategy` that handles regular session tokens and API keys. Using it means: no new secret to provision or rotate, the widget can never see or forward anything with more authority than "this specific logged-in human, right now," and the server-side check is a single GraphQL query — not a bespoke verification scheme to get wrong.

The check deliberately never trusts anything the client asserts about itself (role, user id) — only what `currentUser` reports back for the token presented, fetched fresh every request. A Member who edits the widget's JS to claim `canAccessFullAdminPanel: true` gains nothing: the server never reads that claim from the request.

## The real catch: `currentUser` isn't on the schema agent-runtime already talks to

`agent-runtime`'s existing CRM tools (#43) talk to Twenty's core `/graphql` schema via `TWENTY_API_URL`. `currentUser` is not on that schema — `UserResolver` is `@MetadataResolver`-scoped, meaning it's served only on Twenty's separate `/metadata` endpoint. This was invisible to unit tests (which mock `fetch` entirely) and would have made the real endpoint 401 on every single request, valid token or not — the widget would have looked completely broken despite every unit test passing. Found only by live-verifying against the real Docker stack: querying `currentUser` against `TWENTY_API_URL` returned `"Cannot query field \"currentUser\" on type \"Query\""`, while the same query against `/metadata` succeeded. Fixed by adding a dedicated `TWENTY_METADATA_API_URL` env var (`http://server:3000/metadata` in `ops/docker-compose.yml`) rather than deriving it from `TWENTY_API_URL` by string substitution — an explicit second URL matches how the rest of this codebase configures endpoints (no implicit path-rewriting magic to get wrong later).

Discovering the right endpoint required reading `twenty-server`'s GraphQL config directly, since introspection is disabled for this deployment (`useDisableIntrospectionAndSuggestionsForUnauthenticatedUsers`, on even for authenticated requests here) and the schema is actually split three ways by a `resolverSchemaScope` metadata key (`core` → `/graphql`, `metadata` → `/metadata`, `admin` → `/admin-panel`), each built from a disjoint set of `@CoreResolver`/`@MetadataResolver`/`@AdminResolver`-tagged classes rather than one combined schema.

## A narrow Caddy route, not a network-wide exposure

`agent-runtime` had never been reachable from outside the private Docker network before this ticket. Rather than putting the whole service on the public network, `ops/Caddyfile` adds exactly one `handle /agent-api/widget/message` block (an exact path, not a `/*` wildcard prefix — deliberately, so a future route added to `ManagerWidgetController` doesn't become public just by existing), stripping the `/agent-api` prefix and reverse-proxying only that path to `agent-runtime:3100`; everything else on the service (health checks, the boot-time demo calls, Telegram's own long-polling connection) stays private. Security rests entirely on the per-request token verification `ManagerWidgetController` does, not on network-level restriction — the narrow route is defense in depth, not the actual boundary.

`caddy`'s own `depends_on` for `agent-runtime` uses `condition: service_started`, not `service_healthy` — caught by code review. The first draft used `service_healthy`, which would have meant a crash-looping or never-healthy `agent-runtime` (plausible, given the known pending blockers below) kept `caddy` from starting at all, taking the unrelated core CRM route (`server:3000`) down with it. `reverse_proxy` already degrades gracefully (a 502 on just the one widget path) when its backend isn't reachable, so there's no reason for the whole site to depend on this one new, less-proven service's health.

## Live verification

Performed against the real Docker stack (`tim@apple.dev` dev-seed credentials), chaining Twenty's own two-step interactive login — `signIn(email, password)` on `/metadata` (workspace-agnostic token) → `getAuthTokensFromLoginToken(loginToken, origin)` on `/metadata` (real workspace-scoped access token) — since there's no shortcut: the existing `agent-runtime` static API key doesn't expose `currentUser` either (it isn't tied to a human user), and GraphQL introspection being off meant finding these two mutations required reading `auth.resolver.ts` directly rather than introspecting the schema.

Against the real public route (`https://$DOMAIN/agent-api/widget/message`, proxied through the actual Caddy container):
- No `Authorization` header → **401**, as expected.
- An invalid token → **401**, as expected.
- The real, valid Admin access token → request correctly authenticated and routed to `ManagerAgentService`, reaching the identical pre-existing LLM Guard blocker #43 and #44 already documented (`LlmGuardUnavailableError: fetch failed` — the Anonymize scanner model still can't download from Hugging Face's CDN on this VPS) — a 500, not a 401 or 403. This is the correct proof point: the entire auth/routing stack worked, and the only thing stopping a real reply is the same known, already-documented infrastructure gap, not anything new in this ticket.

One operational gotcha surfaced during this verification, worth recording since it will recur: Caddy's bind-mounted `Caddyfile` is not hot-reloaded by editing the host file plus `caddy reload` alone in this setup — the running container kept serving the previous config's content until the container itself was recreated (`docker compose up -d --force-recreate caddy`). A `Caddyfile` change needs a recreate, not just a reload, to take effect here.
