# Synthetic proof action + true end-to-end integration

Ticket #25 — Phase 2's actual exit criterion. A new whitelisted Controlled Tool API tool (`add-proof-note-to-test-contact`) performs one real, harmless write — adding a note to a designated test contact — and is hardcoded to always require approval. This ADR documents how propose → durable inbox → LangGraph checkpoint → Telegram approval → Controlled Tool API execution → verified Twenty-side effect are actually wired together, not just individually correct, plus the two real gaps this ticket's own live verification uncovered before it ever ran.

**`requiresApproval` is enforced structurally, not by convention.** `ToolDefinition`/`RegisteredTool` gained a `requiresApproval?: boolean` field. `ControlledToolApiService.callTool` rejects any tool registered with it (`ApprovalRequiredError`) — a caller cannot bypass the gate by calling the tool directly with a fabricated identity. The *only* path to real execution is a new `callApprovedTool`, which rejects the opposite case (a tool that does *not* require approval) and is called from exactly one place: `ApprovalService.executeApprovalGatedJob`, once that method has confirmed the approval is `approved` (see below for exactly when it's marked `executed`, which is later than you'd expect). Two entry points, two complementary checks, no way to reach a real write except through a granted approval.

**Jobs only enqueue after approval — carried over from #22, restated here because #25 is what actually exercises it for a real write.** `ApprovalService.propose` never enqueues; only `decide('approved')` does. This means an approval nobody ever responds to is never enqueued at all — ticket #22's own periodic `expireOverduePending` sweep is what actually expires it, not the queued job (which never existed). #25 doesn't change this design, but is the first ticket where "never silently executing without approval" has a real, harmful-if-wrong write behind it, which is why `ProofActionService`'s own boot demo deliberately does *not* auto-approve the way #21's and #22's own demos do — proving a fresh boot proposes but never executes is itself part of what this ticket demonstrates.

**The real tool call happens before `checkAndConsume`, not after — an earlier draft had this backwards.** The obvious-looking order is: atomically claim the approval (`checkAndConsume`, `approved` → `executed`), then do the real work. That's wrong: if the process dies between the CAS succeeding and the tool call completing, the approval is left permanently `executed` even though the Twenty-side write never happened — silent data loss, worse than a duplicate. `executeApprovalGatedJob` calls the tool first; only once it returns does `checkAndConsume` run, to *record* success rather than *authorize* it. A crash during the tool call leaves the approval still `approved`, so BullMQ's own retry re-enters the method and tries the tool again — which is safe only because the tool's own `execute()` is independently idempotent (the next paragraph), not because of this ordering by itself. This is also why `executeApprovalGatedJob` checks `approval.status === 'executed'` directly (fetched before calling the tool) to skip a true retry-after-success, rather than relying solely on `checkAndConsume`'s own `already-executed` outcome for that — the latter is now a rare defense-in-depth catch for a genuine concurrent-worker race, not the common path.

**Two independent, complementary duplicate-protection layers, not one.** `ApprovalRepository.checkAndConsume`'s `approved` → `executed` CAS is what "calling the same action ID twice" actually tests, per the acceptance criteria — it's the durable record of "this ran," checked on every entry via the `approval.status === 'executed'` short-circuit above. Separately, `add-proof-note-to-test-contact`'s own `execute()` checks for an existing note with the same title *before* creating one, making the write itself idempotent regardless of what called it or how many times — this is what actually protects against the tool being called twice (a legitimate retry after a mid-flight crash, as above). Neither alone is sufficient: without the CAS-backed status check, a retry would call the tool again on every single run, relying entirely on the title check; without the title check, the ordering fix above has no defense against calling the tool twice for a genuine retry.

**The designated test contact is found-or-created, not a manual setup step.** `add-proof-note-to-test-contact` looks up a fixed email (`agent-proof-action-target@jai-os.internal`) and creates that Person if it doesn't exist, inside the tool's own `execute()`. This matches every other ticket's convention of a fully automatic boot-time demo needing no manual pre-setup — the alternative (documenting "create this contact by hand first") would be the first ticket in this package to need one.

**LangGraph checkpointing reuses `AgentGraphService`'s existing Postgres connection, not a new one.** `AgentGraphService.checkpointProofAction(threadId, payload)` is a new method on the *existing* service, compiling and invoking a separate, minimal one-node graph against the *same* `PostgresSaver` instance `runDemo` already uses — thread_id is what isolates one run's checkpoint history from another's, not a separate connection or table set. A new `PostgresSaver` per caller was rejected: this RAM-constrained deploy has no spare Postgres connections to spend on a resource that's already shared correctly via `thread_id`. `CONTEXT.md`'s existing warning not to grow `runDemo`/`DemoGraphState` in place is respected — this is a new method and a new graph, not an extension of the demo counter.

**The Twenty API key was never actually generated — every "Token invalid" error since ticket #15 was this.** `ops/.env`'s `AGENT_RUNTIME_TWENTY_API_KEY` was still the literal string `placeholder-not-yet-generated`, discovered while trying to live-verify this ticket's own "Twenty-side effect actually present" requirement, which is the first acceptance criterion in this whole package that actually *needs* a working key (every prior ticket's Controlled Tool API demo call failing was silently tolerated as best-effort). Twenty's own `workspace:generate-api-key` CLI command exists but refuses to run outside `NODE_ENV=development|test` — correctly, since bypassing that guard would circumvent the audit trail the Settings UI provides — so generating the key requires the UI. Fixed by generating a real key through Settings → APIs and updating `.env`.

**Exact GraphQL mutation/field names for Note/NoteTarget/Person were verified against this workspace's own metadata, not guessed from documentation.** `core."objectMetadata"`/`core."fieldMetadata"` (queried directly via `psql`) confirmed `note`/`notes`, `noteTarget`/`noteTargets`, `person`/`people` as the real object names in this exact workspace, and `twenty-server`'s own `create-one-operation-factory.util.ts` confirmed the `create${Capitalize}(data: $input)` / `${Capitalize}CreateInput` mutation convention for workspace data objects (as opposed to the metadata API's unrelated `createOneX` convention, used for platform objects like Role — the two look similar and are easy to conflate). Caddy's self-signed cert for `DOMAIN=localhost` blocked both available browser tools from reaching the UI directly; unblocked by temporarily publishing the `server` container's port 3000 on `127.0.0.1` via a git-ignored `docker-compose.override.yml` (removed immediately after use, not left in place) to reach it over plain HTTP, bypassing Caddy entirely for this one setup step.

## Live verification

Run against the real stack, no mocks, per the acceptance criteria:

- [x] Real, harmless write: `add-proof-note-to-test-contact` registered, `requiresApproval: true`
- [x] End-to-end, one run: `ProofActionService`'s boot demo proposed `proof-action-demo`; `agent_approvals` showed `status: pending`, correct `tool_name`, exact payload; a real checkpoint existed in the `checkpoints` table for `thread_id = 'proof-action-demo'`; `ApprovalService.decide('proof-action-demo', 'approved')` (standing in for a real Telegram tap, per ticket #14's own testing decision) drove it to `status: executed`; a direct GraphQL query against the real workspace confirmed the note exists, correctly linked via `noteTargets` to the auto-created designated contact
- [x] Duplicate protection against the real write: calling `decide('approved')` a second time on the same, already-`executed` action ID was a no-op (`ApprovalService` logs "it was not pending" and never re-submits) — confirmed via a direct GraphQL query showing `totalCount: 1` for the note, same `id` as before
- [x] Second run: worker killed mid-flight (after approval, before the tool call completes) → resumes and completes exactly once on restart. Run against the corrected ordering above: a temporary 20-second delay was added to `execute()` for a `[slow-test]`-tagged payload, the approval was set to `approved` and the job enqueued directly (bypassing a second Nest boot, which an earlier attempt showed creates a competing BullMQ worker in the same container), the real `agent-runtime` container was `SIGKILL`ed ~5s into the delay, and the approval row was confirmed still `approved` (never prematurely `executed`) immediately after the kill. On restart, BullMQ's own stalled-job recovery (not a custom mechanism) picked the job back up once its default stall-detection interval elapsed, re-ran the tool, and `checkAndConsume` then transitioned the row to `executed`. A direct GraphQL query confirmed `totalCount: 1` for the note — exactly one, not zero, not two. The delay hook was reverted immediately after (never committed).

**Known limitation, not fixed here: `findOrCreateDesignatedContact` and the note find-then-create are each a check-then-act race across *different* action IDs.** `ApprovalRepository.checkAndConsume`'s CAS and the note's own title+noteTarget check (above) both protect the same action ID from executing twice; neither protects two *different*, genuinely concurrent approved actions from each independently finding no existing designated contact (or no existing same-titled note) and each creating one. This system's actions are approved one at a time by a single founder tapping a single Telegram chat — concurrent execution of two distinct proof actions is architecturally unlikely, not impossible — so this is accepted as a known gap for Phase 2's scope rather than fixed with, e.g., a DB-level unique constraint on Person email (a Twenty-side schema change out of this package's control) or an application-level lock. Worth revisiting if Phase 3's real agent ever proposes multiple approval-gated actions against the same fixed target concurrently.

## Handoff: what's next

**Current state as of this ADR:** all of Phase 2's tickets (#15–#25) are implemented. This is the phase's own exit criterion — once this ticket's live verification above is complete and merged, Phase 2 (`jai-os-docs/08-build-phases.md`) is done. Phase 3 (a real Manager agent) is the next phase, out of scope for this package's ticket-by-ticket pattern as followed so far.

Where to find the spec: `gh issue view 14` for the parent Phase 2 spec (now fully delivered), `jai-os-docs/08-build-phases.md` for what Phase 3 covers. `CONTEXT.md`'s "Controlled Tool API" and "Approvals" entries describe the two boundaries a real agent will call through — `ControlledToolApiService.callTool` directly for anything that doesn't need approval, `ApprovalService.propose` for anything that does (never `AgentInboxService.submit` directly for an approval-gated action, which would skip the gate).
