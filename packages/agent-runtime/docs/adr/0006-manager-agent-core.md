# Manager agent core: DeepAgents graph + Controlled Tool API tool registration

Ticket #43 — Phase 3's foundation (issue #42's spec). A DeepAgents graph inside `agent-runtime` that resolves a conversational instruction to the correct whitelisted Controlled Tool API call, gates every write through the existing approval mechanism, and reuses Phase 2's guardrail/tracing/provider wiring unchanged. This ADR documents the real integration gap this ticket uncovered — DeepAgents expects a LangChain tool-calling model, `LlmService` didn't have one — and the decisions made to close it without reinventing either side.

## The core gap: DeepAgents is LangChain-native, `LlmService` is Vercel-AI-SDK-native

`01-tech-stack.md` commits to DeepAgents specifically for its sub-agent spawning, declarative permission rules, and human-in-the-loop support — all LangGraph/LangChain-ecosystem features Phase 3 inherits for free by building on it, even though this ticket's own proof-of-concept scope doesn't yet need sub-agents. DeepAgents' `model` parameter accepts a LangChain `BaseLanguageModel`/`LanguageModelLike`, not a Vercel AI SDK model — but `LlmService` (ticket #17) is built entirely on the Vercel AI SDK's `generateText`, and until this ticket had no tool-calling support at all (`generate(prompt: string): Promise<string>` is a single-shot, no-tools, no-history helper). Neither side has a built-in bridge in the other direction: `@ai-sdk/langchain` exists but converts LangChain output *into* AI SDK UI primitives, not an AI SDK model *into* a LangChain chat model.

**Decision: extend `LlmService`, don't replace it, and bridge with a small custom adapter.** `LlmService.generateWithTools(messages, tools)` is a new sibling method next to `generate()` — one non-looping model call per turn (the caller drives the multi-turn tool-call loop; DeepAgents' own LangGraph ReAct loop does this by calling the model repeatedly), using the exact same Fireworks-primary/OpenAI-fallback logic and LLM Guard scanning as `generate()`, refactored into a shared `withFireworksFallback` helper so neither path duplicates the other's retry logic. `LlmServiceChatModel` (`manager-agent/llm-service-chat-model.ts`) is a `BaseChatModel` subclass whose `_generate()` translates LangChain `BaseMessage[]` to Vercel `ModelMessage[]` and back, and whose `bindTools()` converts LangChain `StructuredToolInterface[]` to a Vercel `ToolSet` — a real but narrow translation layer, not new guardrail or provider logic. Every Manager LLM call still goes through LLM Guard and Phoenix exactly as Phase 2 built them; this ticket adds zero new guardrail code.

**Guard scanning scope for a multi-turn tool-calling conversation.** Scanning the *entire* accumulated message history on every turn would re-scan already-cleared content and waste guard calls; `generateWithTools` scans only the newest message in the conversation as input (whatever its origin — a human instruction or a tool result flowing back from Twenty, since CRM data itself could carry injected content) and the resulting text as output, mirroring `generate()`'s own input/output split at the per-turn level rather than the per-conversation level.

## Three generic tools, not thirteen hand-rolled ones

The ticket's registered scope — lookup/create/update across People, Companies, Opportunities, Notes, plus lookup-only Tasks — could have meant five object types × up to three operations each as distinct `ToolDefinition` registrations (matching `add-proof-note-to-test-contact.tool.ts`'s one-tool-one-file precedent). Instead, `lookup-crm-record`, `create-crm-record`, and `update-crm-record` are three generic tools, each dispatching on an `objectType` field via a shared `CRM_OBJECT_REGISTRY` config (`controlled-tool-api/tools/crm/crm-object-registry.ts`) holding each type's GraphQL query/mutation and zod schema. This is a deliberate simplification, not a shortcut on correctness: every acceptance criterion is about *behavior* (the right call for the right object type, Invoice and Task-write structurally unreachable, Opportunity stage locked), and a single `crm:write` scope across the four writable types is sufficient for this phase — no write currently needs finer-grained per-type permission. If a later phase needs to grant write access to Person but not Opportunity, say, that's the point to split back into per-type tools; nothing here makes that migration harder than it already would have been.

**Invoice has no object type entry anywhere, and 'task' has no create/update config.** This is what "no Invoice tools are registered" and "task writes are Phase 6 scope" actually mean structurally: `CRM_OBJECT_TYPES` is a 5-member union that never includes `'invoice'`, and `create-crm-record`/`update-crm-record`'s own `z.discriminatedUnion('objectType', [...])` payload schemas simply have no `'task'` branch. A prompt that talks the model into attempting either fails zod validation at the Controlled Tool API boundary — `InvalidPayloadError`, not a model refusal — the same enforcement shape ticket #25 established for `requiresApproval`.

**Opportunity stage is locked out at the schema, not the prompt.** `OpportunityStageEnum`'s real values were confirmed live via GraphQL introspection against this workspace (`NEW`, `SCREENING`, `MEETING`, `PROPOSAL`, `CUSTOMER`) — `CUSTOMER` is the Closed/Won terminal stage per `04-data-model.md`. Both `opportunityCreateSchema` and `opportunityUpdateSchema`'s `stage` field use `z.enum(['NEW', 'SCREENING', 'MEETING', 'PROPOSAL'])`, excluding `CUSTOMER` entirely — a payload attempting it fails zod validation before `execute()` ever runs, regardless of what the model's prompt says or how it's asked.

**The per-type write config is type-erased for dispatch, same tradeoff `RegisteredTool` already makes.** `CrmObjectConfig`'s `create`/`update` fields are typed `CrmWriteConfig<unknown>` so one `Record<CrmObjectType, CrmObjectConfig>` can hold four structurally different data shapes — but each tool's own discriminated-union payload schema is built from the *real*, individually-exported per-type schemas (`personCreateSchema`, `noteCreateSchema`, etc.), not the erased registry path, so `payload.data` narrows correctly inside `execute()` once `payload.objectType` is checked.

## Approval stays ApprovalService's job, not DeepAgents'

DeepAgents ships its own `interruptOn` human-in-the-loop mechanism. The Manager's write tools don't use it. `create-crm-record`/`update-crm-record`'s LangChain tool wrappers (`manager-agent.service.ts`) call `ApprovalService.propose()` directly — the identical pipeline #22 built and #25 proved end-to-end, including surviving a mid-flight restart — rather than reimplementing approval against DeepAgents' own, different interrupt/resume model. This means every guarantee ticket #25 already verified live (reject → no effect, no double-execution, expiry, exact-payload binding, restart safety) holds for the Manager's own call path for free; this ticket's own tests re-exercise them at the new entry point (via a faithful in-memory stand-in for `ApprovalRepository`'s CAS semantics, not a live database) to confirm the wiring is correct, not to re-derive the state machine from scratch.

## The shared channel interface

`ManagerAgentService.handleMessage({ channel, conversationKey, text })` is what #44 (Telegram) and #45 (widget) both call — neither invents its own `thread_id` scheme. `buildThreadId(channel, conversationKey)` combines both into one LangGraph thread id, reusing `AgentGraphService`'s existing Postgres checkpointer connection (`getCheckpointer()`, a new method mirroring `checkpointProofAction`'s own reasoning: thread_id isolates one conversation from another, not a separate connection).

## Live verification

Blocked on two pre-existing infrastructure gaps this ticket is the first to actually need, neither a regression this ticket introduced — see GATES.md's own G9/G11 entries for the full evidence trail. Tracked as explicit follow-up, not silently left undone:

- [ ] **Blocked — no real LLM provider credentials exist anywhere in this deployment.** `FIREWORKS_API_KEY` and `OPENAI_API_KEY` in `ops/.env` are both still the literal placeholder `"placeholder-not-yet-generated"`, unchanged since ticket #17 — no real LLM call has ever succeeded in this project before this ticket's own diagnostic run. With LLM Guard stubbed for that one diagnostic run only (never committed), the rest of the pipeline proved itself: DeepAgents booted, `LlmServiceChatModel` called real Fireworks (`getaddrinfo EAI_AGAIN`, a DNS/network issue), correctly fell over to real OpenAI, which correctly rejected with "Incorrect API key provided" rather than the call being silently swallowed. That diagnostic run also caught and fixed a real bug: the installed Vercel AI SDK rejects a `system`-role message embedded in `messages` by default (`AI_InvalidPromptError`) — DeepAgents puts its own system prompt there, so `generateWithToolsFromProvider` now passes `allowSystemInMessages: true`. Needs real Fireworks/OpenAI keys before the full instruction-to-Twenty-effect path can be proven live.
- [ ] **Blocked — LLM Guard's Anonymize/PII scanner model cannot download on this VPS.** `deberta-v3-base_finetuned_ai4privacy_v2`'s ONNX weights repeatedly fail with "Read timed out" against Hugging Face's CDN (`us.aws.cdn.hf.co`); confirmed zero bytes ever cached across multiple attempts and a 150-second timeout, despite the host reaching `huggingface.co` itself instantly. This blocks every call to `LlmService.guardInput` — including the pre-existing `generate()` path from ticket #17/#18, not just this ticket's new `generateWithTools` — meaning no live LLM Guard scan has ever actually completed in this project either. Needs the VPS's connectivity to that specific CDN host fixed (or a mirror/proxy configured) before LLM Guard scan activity and a Phoenix trace can be confirmed live for the Manager's calls.
