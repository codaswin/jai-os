# Approvals

Ticket #22. `ApprovalService.propose(actionId, description, payload)` persists a proposed action bound to its exact payload, an expiry, and a status, and sends a Telegram message with inline Approve/Reject buttons via #16's bot. `ApprovalService.decide(actionId, decision)` — called from the Telegram callback handler, or directly in tests, per this ticket's own testing decision — resolves a pending approval. Only on approval does it enqueue a job into #21's queue; execution re-checks status and exact payload match atomically at call time via `ApprovalRepository.checkAndConsume`, not just at proposal time.

**Jobs only enqueue after approval — not at proposal time.** An earlier draft of this design enqueued at `propose()` time and had the job poll a `pending` status. That's dead code: the only thing that ever calls `agentInbox.submit()` for an approval-gated action is `decide()`, and `decide()` only calls it once the row is already `approved` — the queued job can never actually observe `pending`. The real implication: **an approval nobody ever responds to is never enqueued at all**, so nothing would otherwise notice its expiry has passed. `ApprovalService` runs a periodic sweep (`ApprovalRepository.expireOverduePending`, every 60s) that's the actual mechanism behind "expire → never executes" for the realistic case; the job processor's own pending/expiry branch is retained as a defensive check for a caller that bypassed `propose()`/`decide()` and enqueued directly, not the primary path.

**Duplicate protection and approval authorization are two different atomic guards, both required.** `AgentInboxService.submit`'s own action-ID dedup (ticket #21) stops the same action from being queued twice. `ApprovalRepository.checkAndConsume`'s `UPDATE ... WHERE status = 'approved' AND payload = $2::jsonb` stops an approved action from *executing* twice, or executing with a different payload than what was actually approved — a second, independent atomic transition (`approved` → `executed`), gating the real side effect rather than the queue entry. Losing either one reopens a real gap: without the inbox dedup, a redelivered webhook could queue the same approval twice; without the payload-bound CAS, a race between two workers (or a retried job) could execute the same approval's authorization against a payload that was silently swapped after approval.

**An already-executed approval is a success, not a failure, when the job re-runs.** If `markCompleted` (ticket #21's own residual limitation) fails after the real work succeeded, BullMQ retries the whole job — which re-enters `executeApprovalGatedJob`, finds `checkAndConsume` returns `already-executed` (not `consumed`), and returns normally instead of throwing. Treating this as a failure would incorrectly flag an action that actually ran; the CAS itself is what guarantees the real side effect only ever fires once, so a rerun of the *bookkeeping* is safe to treat as a no-op.

**A stale button tap can't approve or reject an action the founder no longer sees as pending.** `ApprovalRepository.decide`'s `UPDATE` is a single atomic statement: `SET status = CASE WHEN expires_at < now() THEN 'expired' ELSE $2 END ... WHERE status = 'pending'`. A decision arriving after the expiry silently becomes `expired` instead of the requested decision, and a decision on a row that isn't `pending` (already decided, or a double-tap) affects zero rows — `ApprovalService.decide` checks the returned record's status against what was requested and no-ops (with a log) on either mismatch.

**Telegram's fire-and-forget callback handling needed its own shutdown fix.** `TelegramBotService.handleUpdate` dispatches a `callback_query` as a detached promise (`.catch(...)`, not awaited by the poll loop) — this predates this ticket (#16) but was harmless until now, since nothing async happened on that path. This ticket's callback handler does real async work (DB writes, a queue enqueue), so a graceful shutdown that began mid-callback could previously have dropped a founder's decision entirely. Fixed by tracking in-flight callback promises in a `Set` and awaiting them in `onModuleDestroy`, the same fire-and-forget-but-tracked pattern `AgentInboxService`/`AgentGraphService` already use for their own boot-time work.

**A generic job-handler registry, not a circular module import.** `ApprovalsModule` needs `AgentInboxService.submit` (to enqueue on approval); the queue's own worker (`AgentInboxWorkerService`, in `AgentInboxModule`) needs to dispatch a job named `approval-gated-action` to `ApprovalService`'s own executor. Importing each module into the other would need `forwardRef()` for what is otherwise a plain "run this named handler" need. `job-handler-registry.ts` is a plain, non-Nest `Map` — `ApprovalService` registers its handler (and its own job options: many more attempts, at a fixed longer interval than the default bounded-retry demo job, since approval jobs need to survive up to the full approval TTL) at `onModuleInit`, and `AgentInboxWorkerService.runJob` looks it up by job name. The same registry also answers `getJobOptions`, so `AgentInboxService.recoverPendingEvents` re-enqueues an orphaned approval job with the *same* long-poll options a normal `submit()` would have used, not the generic defaults — a mismatch here would have silently exhausted a recovered approval job's attempts in seconds instead of surviving to its real expiry.

**Cross-module shutdown ordering: accepted as a narrow residual risk, not solved.** Ticket #21's ADR already established that Nest destroys a module's own providers concurrently, not in dependency order, and fixed that within `AgentInboxModule` with explicit `close()` sequencing. `ApprovalsModule` and `AgentInboxModule`/`TelegramModule` are *separate* modules; Nest destroys whole modules sequentially (reverse of an import-distance ordering), but this repo doesn't rely on that being correct for correctness the way it might be tempting to. In the narrow window where a callback is being processed exactly as shutdown begins, `ApprovalRepository`'s pool could theoretically close before a write from that callback lands — the write throws a clear "pool is closed" error rather than corrupting anything (the approval row simply stays whatever it last durably was), and the founder can just tap the button again after restart. Solving this properly would mean either merging modules or giving `TelegramBotService` a non-lifecycle-hook `close()` method other services could sequence explicitly (as `AgentInboxWorkerService`/`AgentInboxRepository` already do) — out of scope here since #16 has other consumers of `TelegramBotService` that don't need this, and the failure mode is already safe, just occasionally requiring a repeat tap.

## Handoff: what's next

**Current state as of this ADR:** `main` has tickets #15–#22 (this ticket). No tool is actually gated by an approval yet — `ApprovalService`'s own boot-time demo proposes and self-approves a synthetic action, proving the mechanism, not a real one.

**Next unblocked tickets: #23 ("Infra alerts over Telegram," needs only #16) and #24 ("Backups extended to the agent database," needs only #20).** Both are independently available and neither blocks anything else. `#25`, the true end-to-end proof action ("one real, harmless action... proven end-to-end through queue, checkpoint, approval, execution, and a mid-flight restart"), is now unblocked too (needs #21 and #22, both done) and is the ticket that actually wires a real Controlled Tool API call behind `ApprovalService.propose`/`decide` for the first time — this ticket deliberately left that wiring out of scope, per #14's own seam-level testing decision that treats "approval + queue lifecycle" and "true end-to-end, no mocks" as two separate tests.

Where to find the spec: `gh issue view 25` (or `23`/`24` for the other two), `gh issue view 14` for the parent Phase 2 spec, and `jai-os-docs/08-build-phases.md`. Read this package's `CONTEXT.md` "Approvals" entry before wiring #25's real tool call — it needs a `description` string for the Telegram message and a JSON-serializable `payload`, and must call `ApprovalService.propose`, never `AgentInboxService.submit` directly for anything approval-gated (that would skip the approval gate entirely).
